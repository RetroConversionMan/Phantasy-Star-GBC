## Context and lifecycle

The main controller calls `battle_scene_configure(type,palette_index)` before `battle_view_begin`:

- Type0 retains the already rendered standing dungeon view. The caller must first render the canonical standing geometry, including fixed object battles; an old map/NPC canvas cannot stand in for it.
- Types1–32 load the original interaction background with no portrait.
- Types64–75 select the distinct sourceFF room and its floor palette, through `scene_show_room`. These are not scene-table background15.
- For natural world battles, `battle_scene_world_type(group,flags)` applies the exact `GameMode_LoadInteraction` high-nibble remaps: Palma5→4; groups1/7 type1→5; group8→6; group10 type9→8; final zero→1. The flags come from original sample14, playerX−8/playerY−16. Story events supply their actual current scene type, including explicit scene changes before battles.

Ordinary battle overlays never alter the background. On victory `battle_scene_clear` removes enemy OAM and restores8×8 sprite mode; the original scene remains behind subsequent EXP/chest UI. Boss composites restore the original empty scene. This corresponds to15D9/15DC selecting3D36 for interactions or6B3A for standing dungeon geometry. Native dungeon rendering has already supplied the same canonical standing geometry, so removing the overlay restores it without rewriting it. No generic black replacement canvas is inserted.

Window clipping reloads only the current sprite overlay and clears rows beyond the menu's top edge, preventing an8×16 sprite from appearing through the text panel. Full menus hide the overlay; returning restores it. Chest/full-inventory menus likewise hide the chest sprite during full-window selection. Exiting restores8×8 mode and Alis palettes.
